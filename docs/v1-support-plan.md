# First-release support and evidence plan

10 November 2026. Working target: a broad first release covering more than
99% of primary quantitative analyses in a defined psychology benchmark,
with explicit coverage of complex designs. This is an ambition, not an
achieved percentage. Powerkit remains a general research tool.

## What counts as support

A card is a discovery route, not a statistical guarantee. A supported case
must specify the outcome and sampling structure, estimand, actual fitted
model/test, decision or precision goal, parameter range, missing-data
handling, and computational route. Period effects, random slopes, bootstrap
intervals, unequal SDs and ordinal outcomes can change the analysis itself.
A nearby test, generic script requiring a user-written model, or external
package link does not count as implemented support for that case.

Record implementation, sufficient evidence, researcher usability and
remaining restrictions separately. Experimental routes remain available
with explicit limits; they do not count as fully supported until the
relevant release gates pass. A local R script may count as implementation,
but report it separately from an in-app route and test whether the intended
users can actually run it.

The [source inventory](release-support-inventory.json) is generated by
[release-support.R](../scripts/release-support.R) from the same expanded
forms and access metadata the app uses. It includes shared goal selectors,
conditional choices, declared methods and numeric bounds. It lists choices
individually, not valid combinations; generated mediation inputs start at
two mediators. Engine constraints, dynamic UI logic, other generated sizes,
whole-study plans and Labs need explicit case audits too.
Regenerate with `Rscript scripts/release-support.R`; `--check` detects drift.

This is discovery metadata, not a second validation register.
[records.json](../engine/inst/evidence/records.json) and
`analysis_evidence()` remain the evidence source for complete selected
specifications. Do not infer evidence from historical card status,
the existence of a test file, or a successful ordinary check.

## Measure the 99% target

- [ ] Define the sampling frame before collecting examples: eligible
  quantitative psychology studies, publication years, journals/subfields,
  study types and practical exclusions. Include clinical, developmental,
  cognitive/experimental, social/personality, organisational, educational
  and psychometric work. State what the result cannot generalise to.
- [ ] Select papers independently of Powerkit's menu. Use a stratified
  probability sample where possible; record selection probabilities and
  weight the overall estimate appropriately. Keep a separate deliberately
  difficult challenge set. A hand-picked design catalogue cannot establish
  population coverage.
- [ ] Extract study briefs: sampling units, dependencies, outcomes, primary
  claims, analysis, stopping rule, missingness and available planning
  information. Count studies, analyses and papers separately. Two coders
  resolve classifications; report disagreements.
- [ ] Freeze a development set and an untouched assessment set. Do not
  remove difficult studies or change the denominator after seeing failures.
  Unclear cases stay visible, with documented treatment and sensitivity
  analyses.
- [ ] Report primary-analysis coverage, entire-study coverage and correct
  researcher completion separately. Also report evidence-sufficient
  coverage, subfield rates, script-only routes, failures, weights and
  uncertainty. Whole-study coverage requires the actual primary claim
  structure, not merely separate power for each analysis.
- [ ] Plan benchmark size from the intended precision and decision rule.
  A high observed rate in a small sample cannot substantiate a population
  claim above 99%. Account for analyses clustered within papers and
  stratification; get independent review before the final assessment.

No current data justify the 99% claim. Do not advertise it until the
predefined benchmark and uncertainty criterion support it. Broad coverage
is the development goal; narrowing the benchmark is not a substitute.

## Complex-design challenge set

These are audit briefs, not current-support or published-validation claims.
For each, save a complete example spec, intended analysis, known/unknown
inputs, restrictions, route, evidence IDs, failure behaviour and export.
Audit current code first; build only the missing variant.

| Priority | Brief | Distinctions to audit |
| --- | --- | --- |
| P0 | Unequal groups and SDs, score outcomes | Welch versus pooled test; raw units; allocation; rank/robust alternatives; between-study variation restrictions |
| P0 | Three-wave treatment study with dropout | Group-by-time estimand, random slopes/covariance, unequal groups, analysis-specific missingness; growth and repeated ANOVA are not interchangeable |
| P0 | Trials nested in people and crossed with items | Binary/continuous outcomes, participant/item slopes, actual analysis test, singular fits; audit existing E33 limits |
| P0 | Cluster trial with a fixed number of schools | Variable cluster size, allocation, covariates, small-cluster inference, recruitment units and joint outcomes |
| P0 | Repeated counts or ordered ratings | E75 is guidance only; dispersion, zero inflation, thresholds, random effects, actual GLMM/ordinal analysis |
| P0 | Mediation with categorical X, mediator or outcome | Three-group X; binary/count M or Y; scale and interval; score-outcome mediation is not generic coverage |
| P0 | Several primary claims using shared participants | All/any/hierarchical claims; multiplicity, dependence, mixed outcomes and covariates; whole-study simulation remains experimental |
| P1 | Diary/EMA with unequal observations per person | Within/between effects, spacing, autocorrelation, random slopes, missing prompts; distinct from growth and RI-CLPM |
| P1 | Distinguishable dyads over time | Actor/partner dependence, member-specific missingness, moderation; audit E44/E65 before expanding |
| P1 | Counterbalanced AB/BA crossover | Treatment adjusted for period, sequence/carry-over assumptions and withdrawal; the ordinary paired card does not establish power for that adjusted analysis |
| P1 | SEM/CFA and measurement invariance | Unequal multiple groups, ordinal indicators, partial invariance and latent mediation; actual estimator and fit/difference target |
| P1 | EFA and profile selection | Recovery versus choosing factor number; cross-loadings; continuous profiles versus categorical classes; failed fits |
| P1 | Reliability and item fairness | Which ICC, omega/alpha/kappa, rater design, item scale, precision versus a benchmark test; audit E69/E71 |
| P1 | Bayesian fixed and sequential decisions | Design versus analysis priors, stopping, both hypotheses and inconclusive outcomes; posterior precision/ROPE not implied by BF planning |
| P1 | Group-sequential or adaptive frequentist trial | Spending rule, interim timing, stopping and maximum/expected N; Bayesian stopping is not a substitute |
| P1 | Single-case or multiple-baseline study | Randomisation, dependence, effect definition and inference; ITS is not generic single-case support |
| P2 | Survival, diagnostic, prediction and prevalence | Events/censoring, accuracy versus model development, calibration/precision; one proportion covers only scoped prevalence |
| P2 | Meta-analysis, networks and mass-univariate data | Dependent effects, heterogeneity, selection, FDR/network recovery; one corrected test is not whole-pipeline support |

P0 means audit first, not waive validation. Benchmark frequencies and the
severity of wrong answers determine build order. Specialist cases remain
in the challenge set even if rare. Older candidate-package notes do not
approve a backend without checking its current documentation and method.

## Evidence standard for each selected variant

- [ ] Specify aims, data generation, estimand, fitted method and performance
  measures before comparisons. Record nuisance ranges, null/boundary cases,
  small samples, allocation and failure rules.
- [ ] Check argument translation against direct backend calls: exact
  function, scale, units, contrasts, df/test and dependency versions.
  This verifies integration, not independent mathematical validity.
- [ ] Use an independent derivation/implementation or separately generated
  data and fitted analysis. Record shared dependencies and limitations.
  A second wrapper around the same backend is not independent evidence.
- [ ] Check independently transcribed published cases where suitable, with
  source/page/table, settings and a second transcription check. Preserve
  maintainer-owned validation constants and TODOs. If no suitable published
  case exists, record the search and agree an independent standard.
- [ ] Predefine method-appropriate criteria and Monte Carlo precision.
  Discrete/conservative tests need not reject exactly at alpha; equivalence
  and minimum-effect tests need boundary-null checks; Bayes factors need
  evidence probabilities under both hypotheses; EFA/profiles need recovery
  and selection performance, not nominal Type I error checks.
- [ ] Validate the entire intended analysis. Report convergence,
  inadmissible fits, warnings and exclusions. Assess power, calibration,
  interval coverage/bias where relevant, and runtime; do not hide failures
  by analysing successful simulations alone.
- [ ] Recheck returned integer sample sizes with fresh draws independent of
  the search. Show uncertainty and neighbouring feasible sample sizes,
  including cluster/item/sequence constraints.
- [ ] Reproduce saved projects and exported scripts in clean sessions.
  Synthetic data must use the same generator and intended analysis;
  a dataset download alone validates neither.
- [ ] Link summaries, failures, seeds, source SHA, backend/R versions,
  spec hashes and environment through the existing registry. Archive a
  durable release bundle beyond temporary Actions retention, with checksums
  and an immutable archive identifier. Keep inconclusive comparisons.

Use simulation when it represents a requested feature or actual analysis
that the formula cannot. Keep appropriate formula routes. A score-shape
selector or recruitment inflation does not establish generic missing-data,
unequal-variance or rank-analysis support.

## Usability and release gates

- [ ] Unknown inputs have a source, elicitation help, defensible
  range/scenario workflow, or an honest insufficient-information outcome.
  Never silently use zero, perfect reliability or a guessed correlation.
- [ ] Run researcher and accessibility protocols, including fixed budgets,
  unknown nuisance values, adjusted published effects and complex designs.
  Measure correct choices and understanding as well as completion/time;
  compare with the alternatives those researchers would actually use.
- [ ] Resolve mixed-ANOVA GG and model-7 binary-X null failures on a frozen
  candidate. Preserve original tests and explain differences; passing a
  different case does not clear the failing one.
- [ ] Complete independent family review and package-author question packs
  using [release-readiness-review.md](release-readiness-review.md). Replies
  are not endorsement; collaboration/authorship requires explicit agreement.
- [ ] Freeze advertised scope, complete its evidence and benchmark
  assessment, and archive results before a 1.0 claim.
- [ ] Check the actual CRAN tarball on supported systems/current
  dependencies and the complete app separately. Linux R release/devel quick
  CRAN checks passed for v0.60.0; optional backends, scientific validation,
  Windows/macOS CRAN checks and submission work remain.
- [ ] Verify hosted limits and local installation, offline startup, saved
  studies, update compatibility and rollback. A signed desktop installer is
  future work; the current download uses R and a deliberate update check.
